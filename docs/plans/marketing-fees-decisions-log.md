# Marketing fees: decisions log

One line per ambiguity resolved while executing the prompts in `marketing-fees-and-marketer-payouts.md`, for owner review.

- P1: `MarketingFeeService::calculate(..., $applyFlatAmounts)` replaces the plan's `$applyFixed`; false skips BOTH flat amounts (country fixed amount and category variable amount) and keeps only the percentage parts, matching 1.3 and 4.4 (flat amounts charged once, on the first accrual).
- P1: `marketer_campaigns.marketing_fee_fixed_accrued` is a DECIMAL(19,4) (flat amount already accrued, 0 = none yet) instead of a bool, so P6 can see what was charged.
- P1: the ADD migration for `marketer_commission_country_settings` also performs the data copy (`affiliate_commission_amount > 0` -> `affiliate_commission_flat`, mode `fixed`); the legacy dump of dropped values stays in P3 with the DROP. New columns default to mode `percentage`, rate 0, flat 0, share 0.
- P1: no admin UI or seeded row exists for `marketer_campaign_allowed_fulfilment_models`; the only place it is defined is the code default, now one constant `MarketerCampaignService::DEFAULT_ALLOWED_FULFILMENT_MODELS = ['fbn','fbm','cross_dock']` used by all 5 readers. A stored setting row, if an environment has one, still wins and must include `cross_dock` by hand.
- P1: `MarketingFeeType` labels are keyed by value in `lang/{en,ar}/enums/marketing_fee_type.php` (EnumHelpers convention); the Arabic labels keep the Latin codes with "FBN (تنفيذ ناوي)".
- P1: accrual table gets `updated_at` as well as `created_at` (rows change status to settled/reversed); `marketer_payout_wallet_tx_id` has no FK (wallet transaction table is polymorphic across wallet owners).
- P2: new lang file `lang/{en,ar}/marketing_fees.php` (page strings) plus `admin.nav.marketing_fees`; read access is `marketer_commission_settings.view` on the route group, write routes (fixed, variable, delete) add `marketer_fee_settings.edit`; the calculator endpoint is read-only so it needs only the view permission.
- P2: the category select reuses `x-form.async-select` (Select2 AJAX) fed by a new `admin.marketing-fees.categories` endpoint that returns breadcrumb labels ("Parent > Child") and searches name_en/name_ar, limited to 30 hits; the existing page-builder search only matched name_en and had no path.
- P2: variable rows use one form with a "apply to all three types" checkbox (the plan's "copy to all types"), which upserts FBM, FBN and FBP; without it a type is required. The existing-rules list can be filtered by country and each row has a delete button; editing a row = saving the same country/category/type again.
- P2: calculator affiliate mode has a "first accrual" checkbox (default on): off applies only the percentage parts (plan 4.4, flat amounts charged once), via `MarketingFeeService::calculate(..., applyFlatAmounts: false)`. Influencer mode always applies flat amounts. The page seeds the subtotal with 18.90 (plan example).
- P2: Report tab is a text stub only (P8 fills it); the tab is selectable via `?tab=fixed|variable|report` and redirects after saves return to the matching tab.
- P3: `AffiliateCommissionResolver` treats the marketer's profile scope default rule (no category) as part of "the marketer's own rule" (existing `CommissionRuleResolver` order: category chain, then the marketer default); a profile rule that resolves to 0 falls through to the category default.
- P3: a per-unit amount typed on the campaign (admin approval form, peer promotion) still wins at sale time, because `CheckoutPricingEngine` deducts `campaign.marketer_commission_amount x qty` from the vendor payout. The amount stored at approval from the affiliate default is detected (it equals the default computed at the listing price or the real unit price) and is then re-resolved on the real line, so profile rules and percentage defaults apply as the plan says.
- P3: `marketer_commission_amount` on a campaign stays a per-unit number: for a percentage/both default it is the estimate at the listing price (vendor listing, else admin listing; classified listing price for open market). Only influencer-only configurations (fee share set, affiliate default 0) leave it at 0, so `approveCampaign` still refuses to approve them until an amount is typed (unchanged behaviour: before P3 the influencer value was never used for campaign defaults either).
- P3: quote rows for influencers carry `commission` = fee-share payout estimate (`source: fee_share`, `rate` = share %), plus `fee_share_pct`, `marketer_payout`, `platform_keeps` (already what P4 needs) and `per_sale_commission` (profile rule only, D11). Affiliate rows keep `commission` = per-unit estimate with `source` `marketer_rule|category_default|none`. The vendor/admin column header became "Marketer earnings (fee share / commission per unit)".
- P3: the Marketers tab sits inside the category `<form>`, so the old nested per-country `<form>` was dropped by the browser and never reached `updateMarketerCommission`; each country card now saves via fetch (JSON) with `data-field` inputs (no `name`, so nothing leaks into the category update). The controller still redirects for non-JSON requests.
- P3: a mode saves its unused part as 0 (fixed -> rate 0, percentage -> flat 0). Percentages accept 0-100 with up to 4 decimals; flat `decimal:0,4`.
- P3: peer promotion (D12): `resolvePeerCommission` uses the promoter's profile rule at the owner listing price; with no rule the campaign is created with 0 commission and the marketer sees a flash warning (web), a `warning` key (API) and a notice on Active Campaigns (`MarketerCampaign::hasNoPeerCommission()`). The marketer layout gained a `warning` flash.
- P3: the legacy-dump migration (`2026_10_14_150001`) also re-runs the affiliate copy for rows P1 missed (flat still 0) before dumping, writes `storage/app/legacy/marketer_commission_amounts_<date>.json` only when there are rows > 0, and logs the path; the drop is `2026_10_14_150002` (down re-adds both columns as DECIMAL(19,4) default 0, data is not restorable from down()).
- P3: `docs/plans/*` (plan, this log, updates.md) keep the old column names as history; they are outside the section 7 grep scope.
- P4: the snapshot is taken inside `MarketerCampaignService::createCampaign` (not the controller) from a fresh `MarketerCampaignQuoteService::quote()` over the active marketers actually targeted, so every caller (create form, listing create/update) is covered; it is saved only for vendor-owned vendor-listing campaigns (admin/peer/marketer-requested campaigns have no vendor charge and keep NULL columns, shown as "no snapshot").
- P4: `campaign_subtotal` = `total_fee_with_vat` = influencers x (fee + per-influencer VAT rounded half up), i.e. the sum the invitations will be charged; for the plan example this is 18.90 either way. Affiliate-only and zero-influencer campaigns have subtotal 0, so marketing fees and grand total are 0 at creation (their fees accrue per order in P6).
- P4: the wallet-vs-grand-total comparison (balance, shortfall, sufficient) is computed server-side (`MarketerCampaignQuoteService::withWallet`) and added to the `partner.listings.marketer-fee` JSON and the create page, so Alpine only formats numbers; the form now always re-fetches the quote (also when the selection is emptied).
- P4: approval guard change: `approveCampaign` (and `autoApproveCampaign`, same blocker) accept a zero per-unit commission when the campaign's requested marketers are non-empty and ALL influencers (`isInfluencerOnly`); any affiliate in the list, or no marketer list, keeps the refusal / pending-with-notification behaviour. The P3 test that expected the refusal for a fee-share-only influencer campaign was updated to expect approval.
- P4: new strings live in `lang/{en,ar}/marketing_fees.php` under `campaign.*` (shared by the vendor and admin views) via one Blade component `x-marketer-campaign-fee-snapshot`; the vendor success flash now states the grand total (`marketing_fees.campaign.created_with_grand_total`). Admin financials gained "Marketing fees" and "Grand total" columns (snapshot, with the type label) and the requested-marketers partial a grand-total card that prefers the snapshot over the live quote.
- P5: per-invitation marketing share = campaign snapshot `marketing_fee_total` / N (rounded half up 2 dp), which equals plan 4.3 (fixed amount / N + percentage parts on each invitation's equal fee+VAT subtotal) without re-reading settings; N = influencer invitations of the campaign that were not replaced (replacements and affiliates do not count). The last accepted invitation (accepted count + 1 >= N) takes the remainder of the snapshot (never negative), under a lock on the campaign row; campaigns without a snapshot (admin/peer/legacy) get 0 marketing.
- P5: D7 implemented as `platform_fee_payer = 'vendor'` whenever the campaign has a vendor (setting `marketer_influencer_fee_payer` is ignored there); campaigns without a vendor keep the marketer-pays branch, carry no marketing share and no fee share (no vendor charge, so nothing to credit). Peer promotions still have no fee.
- P5: fee share is `platform_fee_amount x share%` (VAT and marketing are not shared), via `MarketerFeeShareResolver` with the product category of the campaign's vendor/admin listing and the campaign country; share % and payout are snapshotted on the invitation at accept time, so later setting changes never alter what is credited.
- P5: new column `payout_items.marketing_fee_amount` (DECIMAL(19,4), new migration) so a statement line reconciles as abs(net) = fee + `vat_amount` + `marketing_fee_amount`; payout item description appends the marketing figure; admin/vendor payout pages and the vendor transactions feed/page expose the separate figure (feed key `marketing_fee`).
- P5: `MarketerFeePayoutService::creditForInvitation` never throws (logs and returns false); it is called after the vendor charge has committed from the wallet path (`collectInfluencerFee`), the weekly statement (`GenerateVendorPayoutsJob`, after its transaction) and the admin "mark fee paid" action (a third paid path), so a frozen marketer wallet cannot undo or block the vendor charge. Skips non-vendor-paid, unpaid, already credited (`marketer_credited_at` / `marketer_payout_wallet_tx_id`), zero payouts and non-influencers.
- P5: retry is `RetryMarketerFeeCreditsJob` scheduled hourly (`retry-marketer-fee-credits` in routes/console.php); it re-runs the same service for paid, vendor-paid invitations with a payout and no credit yet.
- P5: the existing test that expected a marketer-paid fee on a vendor campaign (CampaignInfluencerFeeServiceTest) now asserts D7 (vendor pays, acceptance not blocked) plus a vendor-less campaign for the surviving marketer-pays branch; the partner campaign page no longer casts fee/VAT to int (it dropped decimals such as 0.45).
- P6: the accrual table is unique on (conversion_id, entry_type) instead of conversion_id alone (new column `entry_type` accrual|reversal, migration `2026_10_14_170001`): a reversal is a SECOND row of the same conversion (negative delta, status `reversed`), which a plain unique on conversion_id would forbid. Accrual stays idempotent per conversion; reversal idempotent per conversion.
- P6: who accrues: the conversion's marketer must have the affiliate job and not the influencer job (same test as `AffiliateCommissionResolver`, D11), the campaign must have a vendor (the vendor is the debtor), and the conversion must be approved with a positive `commission_amount` (flash-sale bonus is not part of the base). Accrual runs inside the `ApproveMarketerConversionsJob::approveOne` transaction but a failure is reported and swallowed, so a fee problem can never block the marketer's approval.
- P6: "first accrual" = `marketing_fee_fixed_accrued` is still 0 (P1 column), so a zero-commission order does not consume the flat amounts; `marketing_fee_fixed_accrued` stores the flat part actually charged (total with flats minus total without). Fee type = campaign snapshot, else derived from the listing (`fulfillment_model` / admin `fulfillment_type`); category = order item `commission_category_id`, else the listing's product category.
- P6: reversal = minus the PERCENTAGE parts of the original accrual (calculated again with flats off, capped at the original delta so a changed setting can never over-refund); the flat amount stays accrued. A reversal only exists for conversions that had an accrual (approved ones); a pending conversion reversed before approval never accrued. `campaign.affiliate_fee_accrued` is the cumulative NET accrued (it does not drop when a settlement happens); the settled/unsettled split comes from the rows.
- P6: settlement rule for late events (D4 close): settle() is incremental. It nets every accrual row not yet on a settlement (accrued + reversal rows), creates ONE `marketer_campaign_fee_settlements` row when the net is > 0 and links the rows (accrued -> `settled`, reversal rows keep `reversed`, both get `settled_at`/`settlement_id`). An approval/refund after a settlement stays unsettled and is settled (a) at once when the campaign is already closed (`settleIfClosed` after the approval), or (b) by the next hourly `AffiliateFeeSettlementJob`. A net <= 0 (e.g. a refund after settlement with nothing new accrued) leaves the rows unsettled so they offset later accruals; no wallet credit/refund to the vendor is made in P6 (P7 owns cancellation/refund symmetry).
- P6: "closed" = status cancelled/rejected/done/completed, or status paused with `max_commission_budget > 0` and `commission_budget_spent >= max_commission_budget` (the auto-pause of `LastClickAttributionService`). Triggers: `markCampaignDone` ("finished"), `cancelCampaign`, the budget auto-pause (after its transaction), a late approval on a closed campaign, the hourly job (also retries the wallet for pending settlements), and the admin "Settle now" button (POST `admin.marketer-campaigns.settle-affiliate-fees`, permission `marketer_campaigns.approve`, works on any status).
- P6: vendor debit is wallet-first and all-or-nothing (source_type `marketer_campaign_affiliate_marketing_fee`, source_id = campaign id; one wallet transaction per settlement); if the wallet is short or frozen the settlement stays `pending` and the weekly statement deducts it as payout item `affiliate_marketing_fee` (new enum value; `payout_items.affiliate_fee_settlement_id` unique; `marketing_fee_amount` = abs(net), no VAT per D5). The statement run re-locks each settlement, and the wallet collector re-checks for an existing payout item, so it is paid once either way. The commission itself is untouched (D10).
- P6: marketer panel: new page `marketer.campaigns.show` (linked from Active and Finished campaigns, only for the marketer's own accepted invitation, 404 otherwise) shows ONLY that marketer's own history rows (running total re-accumulated from them) and hides settlement state, the pending-statement notice and vendor wallet data. Vendor and admin pages show the campaign-wide history with settle state; the admin page adds the settle button for `marketer_campaigns.approve`.
- P6: vendor finance: the transactions page gets an "Affiliate marketing fees" type/filter and the feed API a `affiliate_marketing_fee` type (one line per settlement, key `marketing_fee`); the statement detail pages (vendor and admin) show the new line type.
- P7: the only post-payment paths that exist for an ACCEPTED influencer invitation are campaign cancel (`cancelCampaign`, also used by the pending_admin delete) and campaign reject (`rejectCampaign`); reject/timeout/replace only ever touch PENDING invitations (never charged) and there is no "remove accepted marketer" flow. Both paths now call `MarketerInvitationRefundService::refundCampaign`. `done`/`completed` (the work was delivered) does NOT refund. Every vendor-paid accepted influencer invitation of a cancelled/rejected campaign is refunded, whether or not the marketer already posted or received a sample (no work-done exception; the sample/stock flow is unchanged).
- P7: vendor refund = `platformFeeTotal()` (fee + VAT + marketing) credited to the vendor wallet, source_type `marketer_campaign_invitation_platform_fee_refund`, source_id = invitation id. A fee paid through a weekly statement is ALSO refunded through the wallet: issued statements/payout items are immutable and the codebase has no statement adjustment mechanism (the payout item stays as the record, `platform_fee_paid_via` keeps 'statement'). Frozen vendor wallet: the refund is deferred (invitation stays `paid`, the marketer side waits) and `RetryInvitationFeeRefundsJob` (hourly, derives "owed" from cancelled/rejected campaigns, no extra marker) credits it.
- P7: new invitation state in a NEW migration (`2026_10_14_180001`): `platform_fee_refunded_at/_refund_amount/_refund_wallet_tx_id/_refund_reason`, `platform_fee_voided_at`, `marketer_credit_reversed_at`, `marketer_credit_reversal_wallet_tx_id`, `marketer_clawback_amount`; the enum `platform_fee_status` gains `refunded` (paid fees given back; reports that count `paid` as collected no longer count them). A PENDING (unpaid) fee is voided with the existing `waived` status + `platform_fee_voided_at` (labelled "Voided" in the admin view) so the wallet collector, the retry job, the statement selector and admin "mark paid" (all filter `pending`) skip it with no code change.
- P7: marketer reversal runs after the vendor side is settled: wallet debit (source `marketer_campaign_fee_share_reversal`) of `marketer_payout_amount` when the balance covers all of it; short or frozen wallet -> `marketer_clawback_amount` = payout (all-or-nothing, no partial debits, the wallet never goes negative) shown on the marketer wallet page and the invitation rows, recovered by the same hourly job once funded. A credit never made (unpaid fee, frozen marketer wallet) is simply closed (`marketer_credit_reversed_at`, no wallet movement) and `MarketerFeePayoutService` refuses to credit cancelled/rejected campaigns, so a deferred credit can no longer sneak in.
- P7: affiliate refund-after-settlement: a settlement run whose NET of unsettled rows is negative (reversed percentage parts of fees already settled) creates a settlement with `kind = 'refund'` (new column, amount positive, capped at charged minus already refunded) and credits it to the vendor wallet (source `marketer_campaign_affiliate_marketing_fee_refund`, source_id = campaign id); frozen wallet leaves it `pending` for the hourly job. A zero net still creates nothing. Refund settlements are never debited from the wallet and never selected for a statement (`kind = 'charge'` filters). `MarketerConversionReversalService::reverseOne` now calls `settleIfClosed` after the transaction, so a late refund on a closed campaign is credited at once; on an open campaign it stays unsettled and nets into the next settlement as before. The flat amounts stay accrued (P6 rule), so only the percentage part comes back. The P6 test that expected "no refund" was rewritten accordingly.
- P7: the refund appears as a green "Refund after settlement" row in the affiliate fee history on the vendor and admin campaign pages (not on the marketer's, who never sees vendor money), as `affiliate_marketing_fee_refund` in the vendor finance feed/page, and the admin "Settle now" message distinguishes a refund. Influencer refunds show on vendor and admin invitation rows, `influencer_fee_refund` lines in the vendor finance feed/page, and the marketer campaign page (reversed / clawback pending / never credited) plus a clawback card on the marketer wallet page.
